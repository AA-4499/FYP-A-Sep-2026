1.5Risk mitigation
Risk 1: Machine Learning & Digital Twin Skill Gap
The team currently lacks advanced, practical experience in training predictive health models, implementing SHAP frameworks for explainability, and building the core data-driven representation of diabetes progression. This specialized skill gap risks slowing down the development of the core twin engine, leaving the team stuck in the research phase with a poorly performing model, inaccurate "What-If" simulations, and a compromised final academic grade. To mitigate this risk, the team will immediately utilize standard, well-documented open-source machine learning frameworks including Python, Pandas, NumPy, and Scikit-learn, alongside the SHAP library for explainability. The first two weeks of the project plan will be dedicated to intensive online crash courses on predictive health analytics. To ensure project safety, a basic data-driven twin model will be built and validated using the ShanghaiT2DM dataset first, leaving the 3D human representation as a secondary enhancement phase once the core engine functions properly.
Risk 2: Sudden Unavailability or Illness of a Team Member
The project faces a high human capital risk regarding the sudden unavailability, temporary illness, or personal emergency of a core team member mid-semester. The impact of losing a member would cause an extreme workload imbalance, placing the remaining students in a position where critical, deeply dependent components—such as the Neo4j Knowledge Graph, FastAPI backend, or React frontend—risk being completely unintegrated, resulting in a fragmented system that fails the end-to-end Final Demonstration sequence. To mitigate this operational risk, the team will enforce a strict "Two-Person Cross-Functional Rule" where no single member owns a component or codebase exclusively. All source codes will be pushed daily to a shared GitHub repository accompanied by clear internal documentation and code comments. If a member becomes unavailable, the team will immediately scale down the project scope to a Minimum Viable Product (MVP), prioritizing the core data pipeline from patient selection to risk reporting over secondary aesthetic features and the 3D human enhancement.
Risk 3: Lack of Access to Real Clinical Diabetes Data
The team may encounter significant engineering bottlenecks due to a lack of experience when designing meaningful clinical relationships within the Knowledge Graph or writing complex Cypher queries to link the AI risk assessment with personalized insights. If unresolved, the Knowledge Graph will become an isolated data prototype rather than an integrated component, causing the platform to fail in delivering the seamless, contextualized insights required for the final system flow. The team will mitigate this risk by designing a simplified, high-level graph schema focused strictly on key diabetes risk factors and lifestyle relationships before writing any database queries. We will utilize the official Neo4j Python driver within FastAPI or Flask to handle basic data retrieval, and the graph database structural design will be finalized during the initial database design phase to ensure smooth downstream API integration.
Risk 4: Integration and Interoperability Hurdles (API/IoT Skill Gap)
Integrating distinct modules—including the Frontend UI, Relational Database, Neo4j, AI Services, and Digital Twin Simulation—into a unified web application could trigger severe data pipeline integration issues and system latency during live "What-If" simulations, resulting in a buggy presentation and incomplete performance testing data. The team will mitigate these factors by strictly adhering to a modular architecture with a clear, predefined separation of concerns among the front end, backend, AI services, and database layers. A basic, functional end-to-end data pipeline will be built in the very first sprint to catch integration hurdles early. Performance testing and test case generation will be automated early using standard web testing tools to resolve pipeline bottlenecks and reduce user interface latency long before the final evaluation.
Risk 5: Misrepresentation of Clinical Outcomes vs. Simulated Results
The platform faces an ethical and usability risk if it fails to clearly distinguish between a patient's actual longitudinal clinical history from the ShanghaiT2DM dataset and the synthetic predictive results generated during "What-If" simulations. A failure to separate these screens causes the platform to lose its commercial presentability and ethical integrity, risking severe academic grading penalties for presenting unverified algorithmic simulations as real-world patient data. To mitigate this risk, the frontend UI will utilize strict visual anchors, explicit warning labels, and distinct color-coded visualization dashboards built with Plotly, D3.js, or Chart.js to separate historical monitoring from simulation screens. The system architecture documentation and user manual will explicitly map these distinct data flows, ensuring that the final deliverable stands as a cohesive, commercially ready, and ethically sound health management system.
PART 2 Project overview and plan
2.1 problem statement
Diabetes is a chronic condition that requires continuous monitoring of a patient's health status, lifestyle, and diabetes-related risk factors. Patient information is often recorded at different points in time, making it difficult to obtain a clear and holistic view of how a patient's health condition changes over time. This project aims to develop a Smart Diabetes Digital Twin and Personalised Health Management Platform that provides an integrated, patient-centric view of diabetes-related health information. Unlike traditional systems based on single patient records, the proposed platform will utilize the ShanghaiT2DM longitudinal dataset, which contains repeated health records from more than 100 patients with Type 2 diabetes over time, to represent changing health conditions and create a robust digital representation of the patient's health state. The Machine Learning models, data processing, and analytical processes will operate primarily in the backend, while the end-user interface focuses on presenting actionable health information in a clear, intuitive, and commercially presentable manner. The primary objective is to deliver a complete user workflow that seamlessly guides users through patient selection, health history visualization, current risk assessment, key factor analysis, personalized insight exploration, digital twin state viewing, what-if scenario simulation, outcome comparison, and final report generation. Ultimately, the system aims to provide healthcare-related users with a consolidated view of patient data, trends, risk factors, and simulated scenarios, helping them understand complex patient conditions more effectively.

2.5 Solution approach

The platform will be built using a highly modular software architecture that establishes a strict separation between the web frontend, backend services, database storage, AI inference engines, Knowledge Graph components, and the Digital Twin simulation engine. The technical stack incorporates Python for backend logic and analytical processing, leveraging Pandas and NumPy for longitudinal data manipulation, Scikit-learn for machine learning risk assessment models, and SHAP for explainable AI processing. The database layer utilizes Neo4j driven by Cypher queries to handle graph-based health relationships alongside standard data persistence stores. Backend services and API endpoints will be built using FastAPI or Flask to ensure rapid communication with the web client. The frontend presentation layer will be developed using modern web frameworks such as React, integrated with visualization libraries including Plotly, D3.js, or Chart.js to render interactive timelines, risk gauges, XAI contribution plots, and graph nodes.

2.10 Ethical considerations
The platform strictly adheres to the Australian Privacy Principles (APPs) and international health data governance standards. To guarantee patient data privacy and algorithmic transparency, the system implements anonymized data processing on the ShanghaiT2DM dataset and provides SHAP-based feature importance plots for all predictive outputs. Furthermore, to prevent misleading clinical interpretations, a strict Simulation Safety Protocol is embedded into the user interface: all What-If simulation dashboards feature prominent visual disclaimers, distinct color-coded badges, and clear notices explicitly stating that generated scenario projections are non-clinical algorithmic estimates and must not replace professional clinical judgment.
